# 概念

本指南解释了 OpenSpec 背后的核心理念以及它们如何协同工作。有关实际用法，请参阅[入门指南](getting-started.md)和[工作流](workflows.md)。

## 设计理念

OpenSpec 围绕四个原则构建：

```
灵活而非僵化       — 没有阶段关卡，只做有意义的事
迭代而非瀑布       — 在构建中学习，在实践中完善
简单而非复杂       — 轻量级设置，最小化仪式感
棕地优先           — 适用于现有代码库，而不仅仅是全新项目
```

### 为什么这些原则很重要

**灵活而非僵化。** 传统的规范系统将您锁定在各个阶段：先规划，然后实现，然后完成。OpenSpec 更加灵活——您可以按任何对您工作有意义的顺序创建工件。

**迭代而非瀑布。** 需求会变化。理解会深化。刚开始看起来很好的方法，在您查看代码库后可能站不住脚。OpenSpec 接受这一现实。

**简单而非复杂。** 某些规范框架需要大量设置、严格的格式或繁重的流程。OpenSpec 不会妨碍您。几秒钟内完成初始化，立即开始工作，仅在需要时进行自定义。

**棕地优先。** 大多数软件工作不是从零开始构建——而是修改现有系统。OpenSpec 基于增量的方法使得指定对现有行为的变更变得容易，而不仅仅是描述新系统。

## 宏观架构

OpenSpec 将您的工作组织成两个主要区域：

```
┌─────────────────────────────────────────────────────────────────┐
│                        openspec/                                 │
│                                                                  │
│   ┌─────────────────────┐      ┌──────────────────────────────┐ │
│   │       specs/        │      │         changes/              │ │
│   │                     │      │                               │ │
│   │  真实来源            │◄─────│  提议的修改                   │ │
│   │  系统当前工作方式     │ 合并 │  每个变更 = 一个文件夹        │ │
│   │                     │      │  包含工件 + 增量规范           │ │
│   │                     │      │                               │ │
│   └─────────────────────┘      └──────────────────────────────┘ │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**规范** 是真实来源——它们描述系统当前的行为方式。

**变更** 是提议的修改——它们在您准备合并之前位于单独的文件夹中。

这种分离是关键。您可以并行处理多个变更而不会冲突。您可以在变更影响主规范之前对其进行审查。当您归档变更时，其增量规范会干净地合并到真实来源中。

## 规范

规范使用结构化的需求和场景来描述系统的行为。

### 结构

```
openspec/specs/
├── auth/
│   └── spec.md           # 身份验证行为
├── payments/
│   └── spec.md           # 支付处理
├── notifications/
│   └── spec.md           # 通知系统
└── ui/
    └── spec.md           # UI 行为和主题
```

按领域组织规范——对您的系统有意义的逻辑分组。常见模式：

- **按功能区域**：`auth/`、`payments/`、`search/`
- **按组件**：`api/`、`frontend/`、`workers/`
- **按限界上下文**：`ordering/`、`fulfillment/`、`inventory/`

### 规范格式

规范包含需求，每个需求包含场景：

```markdown
# Auth Specification

## Purpose

应用程序的身份验证和会话管理。

## Requirements

### Requirement: User Authentication

系统 SHALL 在成功登录后颁发 JWT 令牌。

#### Scenario: Valid credentials

- GIVEN 具有有效凭据的用户
- WHEN 用户提交登录表单
- THEN 返回 JWT 令牌
- AND 用户被重定向到仪表板

#### Scenario: Invalid credentials

- GIVEN 无效凭据
- WHEN 用户提交登录表单
- THEN 显示错误消息
- AND 不颁发令牌

### Requirement: Session Expiration

系统 MUST 在 30 分钟不活动后使会话过期。

#### Scenario: Idle timeout

- GIVEN 已认证的会话
- WHEN 30 分钟没有活动
- THEN 会话失效
- AND 用户必须重新认证
```

**关键要素：**

| 要素               | 用途                            |
| ------------------ | ------------------------------- |
| `## Purpose`       | 此规范领域的高级描述            |
| `### Requirement:` | 系统必须具备的特定行为          |
| `#### Scenario:`   | 需求在实践中的具体示例          |
| SHALL/MUST/SHOULD  | RFC 2119 关键词，表示需求的强度 |

### 为什么这样组织规范

**需求是“做什么”**——它们陈述系统应该做什么，而不指定实现方式。

**场景是“何时”**——它们提供可以验证的具体示例。好的场景：

- 可测试（您可以为它们编写自动化测试）
- 覆盖快乐路径和边界情况
- 使用 Given/When/Then 或类似的结构化格式

**RFC 2119 关键词**（SHALL、MUST、SHOULD、MAY）传达意图：

- **MUST/SHALL** — 绝对要求
- **SHOULD** — 推荐，但存在例外
- **MAY** — 可选

### 规范是什么（不是什么）

规范是**行为契约**，不是实现计划。

好的规范内容：

- 用户或下游系统依赖的可观察行为
- 输入、输出和错误条件
- 外部约束（安全、隐私、可靠性、兼容性）
- 可以测试或显式验证的场景

规范中应避免：

- 内部类/函数名称
- 库或框架的选择
- 逐步实现细节
- 详细的执行计划（这些属于 `design.md` 或 `tasks.md`）

快速测试：

- 如果实现可以在不改变外部可见行为的情况下更改，那么它很可能不属于规范。

### 保持轻量级：渐进式严谨性

OpenSpec 旨在避免官僚主义。使用仍然能使变更可验证的最轻量级。

**精简规范（默认）：**

- 简短的行为优先需求
- 明确的范围和非目标
- 几个具体的验收检查

**完整规范（适用于高风险）：**

- 跨团队或跨仓库的变更
- API/契约变更、迁移、安全/隐私问题
- 可能因模糊性导致昂贵返工的变更

大多数变更应保持在精简模式。

### 人类与代理的协作

在许多团队中，人类探索，代理起草工件。预期的循环是：

1. 人类提供意图、上下文和约束。
2. 代理将其转换为行为优先的需求和场景。
3. 代理将实现细节保留在 `design.md` 和 `tasks.md` 中，而不是 `spec.md` 中。
4. 验证确认结构清晰，然后才进行实现。

这使得规范对人类可读，对代理保持一致。

## 变更

变更是对系统提议的修改，打包成一个包含理解和实现所需所有内容的文件夹。

### 变更结构

```
openspec/changes/add-dark-mode/
├── proposal.md           # 为什么和做什么
├── design.md             # 如何做（技术方法）
├── tasks.md              # 实现清单
├── .openspec.yaml        # 变更元数据（可选）
└── specs/                # 增量规范
    └── ui/
        └── spec.md       # ui/spec.md 的变化
```

每个变更都是自包含的。它具有：

- **工件**——捕捉意图、设计和任务的文档
- **增量规范**——关于正在添加、修改或删除内容的规范
- **元数据**——此特定变更的可选配置

### 为什么变更使用文件夹

将变更打包为文件夹有几个好处：

1. **一切都在一处。** 提案、设计、任务和规范都位于同一个地方。无需在不同位置寻找。

2. **并行工作。** 多个变更可以同时存在而不冲突。在 `fix-auth-bug` 进行的同时处理 `add-dark-mode`。

3. **清晰的历史记录。** 归档后，变更会移动到 `changes/archive/`，并保留完整的上下文。您可以回溯并理解不仅改变了什么，还有为什么改变。

4. **便于审查。** 变更文件夹易于审查——打开它，阅读提案，检查设计，查看规范增量。

## 工件

工件是变更中指导工作的文档。

### 工件流程

```
proposal ──────► specs ──────► design ──────► tasks ──────► 实现
    │               │             │              │
  为什么          什么          如何           步骤
 + 范围          变更          方法           执行
```

工件相互构建。每个工件为下一个提供上下文。

### 工件类型

#### Proposal (`proposal.md`)

提案在高层次上捕捉**意图**、**范围**和**方法**。

```markdown
# Proposal: Add Dark Mode

## Intent

用户要求添加暗色模式选项，以减少夜间使用时的眼睛疲劳，
并匹配系统偏好。

## Scope

范围内：

- 设置中的主题切换
- 系统偏好检测
- 在 localStorage 中保存偏好

范围外：

- 自定义颜色主题（未来工作）
- 按页面主题覆盖

## Approach

使用 CSS 自定义属性进行主题设置，结合 React 上下文
进行状态管理。首次加载时检测系统偏好，允许手动覆盖。
```

**何时更新提案：**

- 范围变化（缩小或扩大）
- 意图澄清（更好地理解问题）
- 方法发生根本性转变

#### Specs（`specs/` 中的增量规范）

增量规范描述相对于当前规范的**变化**。请参阅下面的[增量规范](#增量规范)。

#### Design (`design.md`)

设计捕捉**技术方法**和**架构决策**。

````markdown
# Design: Add Dark Mode

## Technical Approach

通过 React Context 管理主题状态以避免属性传递。
CSS 自定义属性允许运行时切换，无需切换类。

## Architecture Decisions

### Decision: Context over Redux

使用 React Context 管理主题状态因为：

- 简单的二值状态（亮/暗）
- 没有复杂的状态转换
- 避免添加 Redux 依赖

### Decision: CSS Custom Properties

使用 CSS 变量而不是 CSS-in-JS 因为：

- 适用于现有样式表
- 无运行时开销
- 浏览器原生解决方案

## Data Flow

```
ThemeProvider (context)
       │
       ▼
ThemeToggle ◄──► localStorage
       │
       ▼
CSS Variables (applied to :root)
```

## File Changes

- `src/contexts/ThemeContext.tsx`（新增）
- `src/components/ThemeToggle.tsx`（新增）
- `src/styles/globals.css`（修改）
````

**何时更新设计：**

- 实现显示方法不可行
- 发现更好的解决方案
- 依赖或约束发生变化

#### Tasks (`tasks.md`)

任务是**实现清单**——带有复选框的具体步骤。

```markdown
# Tasks

## 1. Theme Infrastructure

- [ ] 1.1 创建带亮/暗状态的 ThemeContext
- [ ] 1.2 为颜色添加 CSS 自定义属性
- [ ] 1.3 实现 localStorage 持久化
- [ ] 1.4 添加系统偏好检测

## 2. UI Components

- [ ] 2.1 创建 ThemeToggle 组件
- [ ] 2.2 在设置页面添加切换开关
- [ ] 2.3 更新 Header 包含快速切换

## 3. Styling

- [ ] 3.1 定义暗色主题调色板
- [ ] 3.2 更新组件以使用 CSS 变量
- [ ] 3.3 测试对比度比率确保可访问性
```

**任务最佳实践：**

- 在标题下对相关任务进行分组
- 使用层级编号（1.1、1.2 等）
- 保持任务足够小，可以在一次会话中完成
- 完成任务时勾选

## 增量规范

增量规范是使 OpenSpec 适用于棕地开发的关键概念。它们描述**正在变化的内容**，而不是重述整个规范。

### 格式

```markdown
# Delta for Auth

## ADDED Requirements

### Requirement: Two-Factor Authentication

系统 MUST 支持基于 TOTP 的双因素认证。

#### Scenario: 2FA enrollment

- GIVEN 未启用 2FA 的用户
- WHEN 用户在设置中启用 2FA
- THEN 显示用于认证应用设置的二维码
- AND 用户必须在激活前使用验证码验证

#### Scenario: 2FA login

- GIVEN 启用了 2FA 的用户
- WHEN 用户提交有效凭据
- THEN 显示 OTP 挑战
- AND 仅在有效 OTP 后完成登录

## MODIFIED Requirements

### Requirement: Session Expiration

系统 MUST 在 15 分钟不活动后使会话过期。
（之前：30 分钟）

#### Scenario: Idle timeout

- GIVEN 已认证的会话
- WHEN 15 分钟没有活动
- THEN 会话失效

## REMOVED Requirements

### Requirement: Remember Me

（已弃用，改为使用 2FA。用户应每次会话重新认证。）
```

### 增量部分

| 部分                       | 含义         | 归档时发生什么 |
| -------------------------- | ------------ | -------------- |
| `## ADDED Requirements`    | 新行为       | 追加到主规范   |
| `## MODIFIED Requirements` | 改变的行为   | 替换现有需求   |
| `## REMOVED Requirements`  | 已弃用的行为 | 从主规范中删除 |

### 为什么使用增量而不是完整规范

**清晰性。** 增量准确显示正在变化的内容。阅读完整规范，您需要将其与当前版本进行心理比较。

**避免冲突。** 两个变更可以触及同一个规范文件而不会冲突，只要它们修改不同的需求。

**审查效率。** 审查者看到的是变化，而不是未变化的上下文。专注于重要内容。

**棕地适应性。** 大多数工作修改现有行为。增量使修改成为一等公民，而不是事后考虑。

## 模式

模式定义了工作流的工件类型及其依赖关系。

### 模式如何工作

```yaml
# openspec/schemas/spec-driven/schema.yaml
name: spec-driven
artifacts:
  - id: proposal
    generates: proposal.md
    requires: [] # 无依赖，可以首先创建

  - id: specs
    generates: specs/**/*.md
    requires: [proposal] # 创建前需要提案

  - id: design
    generates: design.md
    requires: [proposal] # 可以与规范并行创建

  - id: tasks
    generates: tasks.md
    requires: [specs, design] # 需要规范和设计
```

**工件形成依赖图：**

```
                    proposal
                   （根节点）
                       │
         ┌─────────────┴─────────────┐
         │                           │
         ▼                           ▼
      specs                       design
   （需要：                      （需要：
    proposal）                    proposal）
         │                           │
         └─────────────┬─────────────┘
                       │
                       ▼
                    tasks
                （需要：
                specs、design）
```

**依赖是启用器，不是关卡。** 它们显示什么可以创建，而不是下一步必须创建什么。如果您不需要设计，可以跳过它。您可以在设计之前或之后创建规范——两者都只依赖于提案。

### 内置模式

**spec-driven**（默认）

规范驱动开发的标准工作流：

```
proposal → specs → design → tasks → 实现
```

最适合：大多数功能开发，您希望在实现前就规范达成一致。

### 自定义模式

为团队的工作流创建自定义模式：

```bash
# 从头创建
openspec schema init research-first

# 或派生现有模式
openspec schema fork spec-driven research-first
```

**自定义模式示例：**

```yaml
# openspec/schemas/research-first/schema.yaml
name: research-first
artifacts:
  - id: research
    generates: research.md
    requires: [] # 先进行研究

  - id: proposal
    generates: proposal.md
    requires: [research] # 提案基于研究

  - id: tasks
    generates: tasks.md
    requires: [proposal] # 跳过规范/设计，直接进入任务
```

有关创建和使用自定义模式的完整详细信息，请参阅[自定义](customization.md)。

## 归档

归档通过将变更的增量规范合并到主规范中并保留变更以供历史追溯来完成变更。

### 归档时发生什么

```
归档前：

openspec/
├── specs/
│   └── auth/
│       └── spec.md ◄────────────────┐
└── changes/                         │
    └── add-2fa/                     │
        ├── proposal.md              │
        ├── design.md                │ 合并
        ├── tasks.md                 │
        └── specs/                   │
            └── auth/                │
                └── spec.md ─────────┘


归档后：

openspec/
├── specs/
│   └── auth/
│       └── spec.md        # 现在包含 2FA 需求
└── changes/
    └── archive/
        └── 2025-01-24-add-2fa/    # 保留供历史追溯
            ├── proposal.md
            ├── design.md
            ├── tasks.md
            └── specs/
                └── auth/
                    └── spec.md
```

### 归档过程

1. **合并增量。** 每个增量规范部分（ADDED/MODIFIED/REMOVED）都会应用于对应的主规范。

2. **移至归档。** 变更文件夹移动到 `changes/archive/`，并带有日期前缀以便按时间顺序排列。

3. **保留上下文。** 所有工件在归档中保持不变。您可以随时回溯以理解为什么做出变更。

### 为什么归档很重要

**清晰状态。** 活跃变更（`changes/`）仅显示进行中的工作。已完成的工作移出视线。

**审计追踪。** 归档保留了每个变更的完整上下文——不仅是什么变更，还有解释为什么的提案、解释如何做的设计，以及显示已完成工作的任务。

**规范演进。** 随着变更被归档，规范有机增长。每个归档合并其增量，随着时间的推移逐步构建全面的规范。

## 一切如何协同工作

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                              OPENSPEC 流程                                   │
│                                                                              │
│   ┌────────────────┐                                                         │
│   │  1. 启动       │  /opsx:propose（核心）或 /opsx:new（扩展）              │
│   │     变更       │                                                         │
│   └───────┬────────┘                                                         │
│           │                                                                  │
│           ▼                                                                  │
│   ┌────────────────┐                                                         │
│   │  2. 创建       │  /opsx:ff 或 /opsx:continue（扩展工作流）               │
│   │     工件       │  创建 proposal → specs → design → tasks                 │
│   │                │  （基于模式依赖关系）                                    │
│   └───────┬────────┘                                                         │
│           │                                                                  │
│           ▼                                                                  │
│   ┌────────────────┐                                                         │
│   │  3. 实现       │  /opsx:apply                                            │
│   │     任务       │  完成任务，逐项勾选                                      │
│   │                │◄──── 边学习边更新工件                                    │
│   └───────┬────────┘                                                         │
│           │                                                                  │
│           ▼                                                                  │
│   ┌────────────────┐                                                         │
│   │  4. 验证       │  /opsx:verify（可选）                                   │
│   │     工作       │  检查实现是否与规范匹配                                  │
│   └───────┬────────┘                                                         │
│           │                                                                  │
│           ▼                                                                  │
│   ┌────────────────┐     ┌──────────────────────────────────────────────┐   │
│   │  5. 归档       │────►│  增量规范合并到主规范                         │   │
│   │     变更       │     │  变更文件夹移至 archive/                      │   │
│   └────────────────┘     │  规范现在成为更新后的真实来源                 │   │
│                          └──────────────────────────────────────────────┘   │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

**良性循环：**

1. 规范描述当前行为
2. 变更提议修改（作为增量）
3. 实现使变更成为现实
4. 归档将增量合并到规范
5. 规范现在描述新行为
6. 下一个变更建立在更新的规范之上

## 术语表

| 术语         | 定义                                                     |
| ------------ | -------------------------------------------------------- |
| **工件**     | 变更中的文档（提案、设计、任务或增量规范）               |
| **归档**     | 完成变更并将其增量合并到主规范的过程                     |
| **变更**     | 对系统提议的修改，打包为包含工件的文件夹                 |
| **增量规范** | 描述相对于当前规范的变化（ADDED/MODIFIED/REMOVED）的规范 |
| **领域**     | 规范的逻辑分组（例如 `auth/`、`payments/`）              |
| **需求**     | 系统必须具备的特定行为                                   |
| **场景**     | 需求的具体示例，通常采用 Given/When/Then 格式            |
| **模式**     | 工件类型及其依赖关系的定义                               |
| **规范**     | 描述系统行为的规范，包含需求和场景                       |
| **真实来源** | `openspec/specs/` 目录，包含当前商定的行为               |
| **模式**     | 工件类型及其依赖关系的定义                               |
